# Security guarantees

kalkan audits code that you do not trust. This document states what kalkan guarantees, how each guarantee is enforced, what leaves the machine, and which risks remain. The Turkish summary is in [README.tr.md](../README.tr.md#güvenlik-güvenceleri).

## The guarantees

1. **kalkan never modifies the audited project.** No file and no folder of the target changes. No process runs inside the target folder, except one read-only git process that copies the history (see promise 1).
2. **The kalkan agents act only on their own result file.** A subagent reads the target copy and its task files, and writes exactly one file: its own `result.json`. It has no shell, no web access and no MCP tools.
3. **No data leaves the machine, except the traffic of your own Claude session to Anthropic.** By default no scanner, no SCA tool and no engine command uses the network. The setup downloads, the database update, the clone of a git URL target, the sandbox base images of `kalkan sandbox pull` and the opt-in `--online` flag are the only other network uses, and you start each of them yourself. `kalkan audit` runs the setup downloads only with `--yes` or after you answer `y` to its question.

## Promise 1: the audited project is never modified

| Mechanism | Where |
|---|---|
| `run init` copies the target into `runs/<run-id>/target/`. It only reads the original: bounded reads, no link is followed, new files are written with exclusive create inside the run folder only. | `src/kalkan/run/init.py` (`copy_tree`) |
| A local git work tree gets a private mirror of its history in `runs/<run-id>/source/`: `git clone --mirror --no-local --template=` with `core.fsmonitor=false`, `core.symlinks=false`, `GIT_ALLOW_PROTOCOL=file` (only for this clone), `GIT_NO_LAZY_FETCH=1` and prompts off. The working folder of the clone is the run folder. After the clone, the `remote.origin` section is removed, so the copy has no link back to the original. | `src/kalkan/run/init.py` (`copy_history`) |
| `--upload-pack` sets `transfer.hideRefs=!refs/` and `uploadpack.hideRefs=!refs/`, so a repository config cannot hide refs from the history scan. | `src/kalkan/run/init.py` |
| `git_ref` comes from `git rev-parse HEAD` in the copy. A folder inside a work tree (not its root) gets `git_ref` from the files of the git folder (`HEAD`, a loose ref, `packed-refs`). No git process runs for it. | `src/kalkan/run/init.py` (`read_head`) |
| A history copy that fails (for example a repository that another user owns) is not fatal. The manifest field `history` records the reason, `source_dir` is null, and `gitleaks-history` is skipped with that reason. | `src/kalkan/run/init.py`, `src/kalkan/scanners/adapters/gitleaks.py` |
| `run init` refuses a runs folder inside the target folder. Set `KALKAN_RUNS_DIR` to a folder outside the target. | `src/kalkan/run/init.py` |
| No scanner gets the original path. `load_scan_context` accepts `source_dir` only when it is inside the run folder, and `gitleaks-history` and `kingfisher-history` check it again. The working folder of every tool is a run folder (`scans/`, `sca/`, or a folder of the target copy). | `src/kalkan/scanners/base.py`, `src/kalkan/scanners/adapters/gitleaks.py` |
| `gitleaks git` reads the copy with `GIT_OPTIONAL_LOCKS=0` and `GIT_NO_LAZY_FETCH=1`, and with `--no-textconv --no-ext-diff`, so git runs no command of the repository config. | `src/kalkan/scanners/adapters/gitleaks.py` |

**Tests.** `tests/integration/test_security_promises.py` builds a repository with traps: a `core.fsmonitor` command, a textconv driver, a clean and smudge filter, a hook for every git event, a hidden branch, a stash and a detached HEAD. It hashes every file and folder of the repository, `.git` included, with its size and modification time. After `run init` (and, with `@pytest.mark.tools`, after `scan all`, `sca sbom` and `sca match` with the real tools) the snapshot is identical and no trap fired. A control step runs `git log -p` in the original and sees the textconv trap fire, so the traps work. Other tests check that every adapter command line, working folder and environment is free of the original path, that a failed copy is recorded, and that the hidden branch and the stash reach the copy.

## Promise 2: the agents act only on their result file

### Checkout mode (`.claude/settings.json`)

| Mechanism | Where |
|---|---|
| Allow only the engine (`.venv/Scripts/kalkan.exe`, `.venv/bin/kalkan`), Read, Grep, Glob and `Edit(/runs/*/tasks/*/result.json)`. | `.claude/settings.json` |
| Deny `WebFetch`, `WebSearch`, `curl`, `wget` and `git push` for Bash and PowerShell, `Invoke-WebRequest`, `Invoke-RestMethod`, `iwr` and `irm` for PowerShell, edits below `.git/`, and reads of `.env` files. | `.claude/settings.json` |
| Every kalkan agent has the tool list `Read, Grep, Glob, Write` (the translator and the polisher: `Read, Write`) and `disallowedTools: Bash, WebFetch, WebSearch, Edit, NotebookEdit` (the translator and the polisher also `Grep, Glob`). Claude Code offers an agent only the tools of its list, so it has no shell, no web tool and no MCP tool. | `.claude/agents/kalkan-*.md` |
| Every task prompt says: read only, write exactly one file, no execution, no network. | `src/kalkan/prompts/_common.md` |

**No deny rule for edits outside `runs/`.** Claude Code never lets a local setting override a deny rule. An `Edit` deny for `src/`, `tests/` or `docs/` would block every development session in this repository. The checkout therefore denies only edits below `.git/`. The agents are limited by their tool lists and by the allow list instead. A test (`tests/unit/test_security_settings.py`) keeps this choice.

### Plugin mode (`kalkan.plugin_hook`)

A plugin cannot ship permission rules. The PreToolUse hook (`plugins/kalkan/hooks/hooks.json`, `plugins/kalkan/hooks/pre-tool-use.sh`, `src/kalkan/plugin_hook.py`) gives the decisions.

**A kalkan subagent** (`agent_type` starts with `kalkan:`) gets `allow` or `deny` for every call that reaches the hook, never the normal flow:

- Read, Grep and Glob: `allow` only inside `<runs>/<run-id>/target/` or `<runs>/<run-id>/tasks/`. A `.env` file gets `deny`. One more Read is allowed: a saved output of a tool call of the same Claude Code session (`<Claude config>/projects/<project>/<session>/tool-results/<name>.txt`, a regular file after links are resolved). Claude Code writes a large tool output there and tells the agent to read it; the content is the output of a call that the hook already allowed. Grep and Glob without a path search the event `cwd`, which must be inside these folders too.
- The first Read of `tasks/<task-id>/prompt.md` binds the agent (`agent_id`) to that run and task (`<data>/hook/agents/<agent_id>.json`). After that, reads must stay in the bound run.
- Write: `allow` only for `result.json` of the bound task, in an existing task folder that is not a link. Without a binding, every write gets `deny`.
- Every other tool gets `deny`: Bash, PowerShell, Edit, MultiEdit, NotebookEdit, WebFetch, WebSearch, every `mcp__` tool, Agent and the rest.
- When the hook itself fails, a kalkan subagent call gets `deny` (fail closed). A call of the user gets no output (fail open).

**Path matching** is robust on Windows: `\` and `/` are the same, an MSYS path (`/c/Users/...`) becomes `c:/Users/...`, the case is folded, a relative path is joined to the event `cwd`, and `os.path.realpath` resolves `..`, symlinks, junctions and 8.3 short names before the comparison.

**The main session and other agents:**

- The hook allows one engine command at a time (`<data>/venv/.../kalkan`, no shell operator, no `$`, no backtick) and the setup command. It allows Read, Grep and Glob inside the data folder and the runs root, and denies `.env` reads there.
- An engine command marks the session as an active kalkan orchestration (`<data>/hook/sessions/<session_id>.json`). While the mark is active, the hook denies the network tools of that session: WebFetch, WebSearch, every MCP tool, and Bash or PowerShell commands that name a network program (`curl`, `wget`, `ssh`, `scp`, `nc`, `Invoke-WebRequest`, ...), a URL, a git transfer (`push`, `pull`, `fetch`, `clone`, `ls-remote`) or a package download.
- The mark ends when the run reaches the phase `done`, or 6 hours after the last engine command of the session.
- Other sessions are never denied anything. Every other call follows your normal permission settings, and your own deny rules still win over a hook `allow`.

**What reaches the hook.** Each hook call starts Git Bash on Windows (about 0.2 s for an unrelated call, measured on 2026-10-16). To keep unrelated sessions fast, `hooks.json` starts the launcher only for: Read, Grep, Glob, Write, NotebookEdit, WebFetch, WebSearch and every MCP tool; Bash commands that contain `kalkan` or a network word (`if` filters such as `Bash(*curl*)`, `Bash(*http*)`, `Bash(*git push*)`); and PowerShell commands with a network word. The launcher then exits at once, without Python, unless the event mentions `kalkan` or a session has an active mark.

**Tests.** `tests/unit/test_plugin_hook.py` covers the subagent policy (every other tool denied, reads outside the run denied, `..`, junctions, case and MSYS forms, the binding, writes to another task denied, fail closed), the session mark (network tools denied only in the marked session, the end at `done` and after 6 hours, unsafe session IDs) and the network word list. `tests/unit/test_build_plugin.py` checks the matchers, the unique handler commands and the quick filter of the launcher.

### Codex mode

A Codex custom agent cannot have its own tool list or sandbox (docs/CODEX.md). The project config turns off the network for every Codex session (`workspace-write` without network access, no web search). Read-only access and the single result file are enforced by the instructions only.

**Version probes** (PROGRESS K.1). `kalkan doctor` and `resolve` start the version command of every manifest tool (`version_args`), `go env GOVERSION` and a package query of the tool venv. These commands never get the environment of the user: they run with the minimal tool environment of the adapters (no token, no `GOFLAGS`, no `PYTHONPATH`; the proxy variables stay), the update-check and telemetry switches of the manifest (`version_args`, `version_env`) and a new empty working folder, so that no configuration file of the current folder is read (`kalkan.tools.resolve.probe_env`, docs/ENGINE-SPEC.md section 12). That folder is also the temporary folder of the probe and, for a Go program, its Go configuration folder with telemetry off; it is removed after the probe (see [What kalkan writes where](#what-kalkan-writes-where)). Measured before the change on 2026-10-25: `checkov --version` connected to `pypi.org` and `govulncheck -version` to `vuln.go.dev`; after it: zero connections for every manifest tool (20 tools on that day).

**Secret values never reach a kalkan file.** Gitleaks runs with `--redact`. Kingfisher runs with `--redact`: it writes every value and validation response as `[REDACTED:<salted hash>]`. The adapter reads its JSON report from the work folder, fails the run when a snippet or a validation response is not redacted, writes its own SARIF (snippet `REDACTED`, no Kingfisher fingerprint, which is an XXH3-64 hash of the value and its offsets and would confirm a guessed weak password; no author or e-mail of a commit) and deletes the report, also after a failed run. `--quiet` keeps findings out of the logs. Tested: a made-up unredacted value fails the run and appears in no file of the run folder; on the vulnapp fixture and on a history copy no planted value appears in `scans/` or `candidates.json`.

**Local vulnerability databases** (`src/kalkan/sca/vulndb.py`). `kalkan sca update-db` downloads them into the kalkan home:

- OSV: OSV-Scanner downloads `<ecosystem>/all.zip` for 13 ecosystems (npm, PyPI, Go, Maven, RubyGems, Packagist, crates.io, NuGet, Pub, Hex, CRAN, SwiftURL, GitHub Actions; about 290 MB) for a probe file with one made-up package per ecosystem. The request names only the ecosystem. `--ecosystems` selects others.
- Grype: `grype db update`, then `grype db status`.
- Go (govulncheck): the official archive `https://vuln.go.dev/vulndb.zip` (go.dev/security/vuln/database, "Bulk download"; 3.4 MB, 4,613 entries on 2026-10-16; the name `vuln.zip` does not exist and answers with an HTML page). It is a plain GET request. kalkan accepts only an HTTPS answer with a zip content type and the zip signature, checks the layout (`index/db.json`, `index/modules.json`, `ID/<id>.json`, every entry valid) and writes only the names of that layout into `<home>/.tools/vulndb/go/`. When the download fails, kalkan builds the same layout from the `GO-*.json` entries of the OSV Go archive (`--go-source osv` asks for it directly). `kalkan-source.json` records the source and the `modified` time; `kalkan doctor` shows both. A failed update keeps the old database.
- RetireJS (the vendored JavaScript check of `sca match`): one GET request for the library repository `jsrepository-v5.json` of RetireJS/retire.js on raw.githubusercontent.com (the file of the retire 6.1.0 command line). kalkan accepts only an HTTPS answer with a text or JSON content type, at most 32 MiB, that parses as a usable repository, and stores it with its SHA-256 in `<home>/.tools/vulndb/retire/`. kalkan reads it as data: no RetireJS code runs. The extractors run in a child process of kalkan (`python -I`, working folder in the run folder, a time limit per file); see docs/ENGINE-SPEC.md section 17.
- `kalkan sca update-db` downloads a database only when it must: a database whose files are valid, whose last download ended `ok` and that is younger than 24 hours (`--max-age HOURS`) is kept; `--force` downloads all of them. `scripts/bootstrap.ps1`, `scripts/bootstrap.sh`, the plugin setup (`kalkan-setup`) and the setup of `kalkan audit` run it with `--max-age 168` (7 days), so a new setup or a plugin update within a week sends no database request. A failure only warns. `kalkan doctor` warns (check `vulndb`) when a database is missing or older than 7 days (the oldest part counts).

**A missing database is a gap, never an online query.** In local mode a matcher without a database is skipped, and an ecosystem without a database stops OSV-Scanner (it reports `could not load db for <ecosystem> ecosystem`). Without the local RetireJS repository the vendored JavaScript check is skipped. `sca match` records each case in the `database_gaps` list of `sca/vulns.json`, and the report lists them as scan gaps and as a partial-result reason.

The tool tests of 2026-10-25 were run again after the re-pin to zizmor 1.30.1, OpenSSF Scorecard 5.5.0, Kingfisher 2.11.1 and gixy 0.2.55 (ADR-0005 rule 1): zero connections, and the control steps still see the trap.

## What kalkan writes where

kalkan keeps its files in two folders: the kalkan home (the checkout, or `~/.claude/plugins/data/kalkan-kalkan` for the plugin; `KALKAN_HOME` moves it) and the runs root (`runs/` of the checkout, `~/kalkan-runs` for the plugin; `KALKAN_RUNS_DIR` moves it). `kalkan clean` shows the size of each part and deletes it; `kalkan run clean <run-id>` deletes the target copy and the work folders of a finished run.

| Folder | Content |
|---|---|
| `<home>/.tools/<tool>/`, `.tools/go/`, `.tools/pyenv/`, `.tools/installed.json` | the pinned tools |
| `<home>/.tools/vulndb/` | the vulnerability databases |
| `<home>/.tools/cache/` | data that tools keep between runs and that holds nothing of a target: the unpacked runtime of opengrep |
| `<home>/.tools/go-build/`, `<home>/.tools/.tmp/` | the build and download folders of `kalkan tools install`, removed after use |
| `<runs>/<run-id>/` | one run: the target copy, the history copy, the tool results, the work folders of the tools (`scans/.work/`, `sca/.work/`), the agent tasks and the report |

**No kalkan tool writes outside these folders.** Measured on Windows 11 on 2026-10-29: the user profile (names, modification times, sizes) was snapshotted before and after `kalkan doctor`, `kalkan scan all` and `kalkan sca sbom`, `match` and `reach` on a run of the vulnapp fixture. Before the change:

- opengrep wrote its log `~/.opengrep/semgrep.log` (262 KB of target paths and matched code; the version probe of the doctor wrote it too), unpacked its runtime into `%USERPROFILE%\AppData\Local\opengrep\v1.30.1` (277 MB in 84 files) and left 58 files (5.4 MB: `semgrep-*.rules` and its core input and output) in `%TEMP%`.
- gosec and govulncheck filled the Go build cache `%LOCALAPPDATA%\go-build` (gosec 1,464 files, 93 MB; govulncheck 3 more).
- Go wrote telemetry counters below `%APPDATA%\go\telemetry` (the Go command, the compiler and govulncheck write them once that folder exists).
- pip kept the downloads of `kalkan tools install` in the pip cache of the user.

| Who | Where it writes now (`kalkan.tools.toolhome`) |
|---|---|
| every tool run of a scanner or SCA adapter | `TEMP`, `TMP` (and `TMPDIR` on Linux and macOS) = `tmp/` in the work folder of the run |
| opengrep, opengrep-packs | `USERPROFILE` and `HOME` = `<home>/.tools/cache/opengrep` (its runtime, once per version); the log (`SEMGREP_LOG_FILE`, `XDG_CONFIG_HOME`) in the work folder of the run |
| gosec, govulncheck | `GOCACHE` and the Go configuration folder (with `go/telemetry/mode` `off`) in the work folder of the run; with `--online` also `GOPATH` (module downloads) |
| version probes (`kalkan doctor`) | the empty probe folder is the temporary folder, and for a Go program the Go configuration folder with telemetry off; it is removed after the probe |
| `go install` builds of `kalkan tools install` | `GOTMPDIR` and the Go configuration folder with telemetry off below `.tools/go-build`, which is removed after the builds |
| pip (`kalkan tools install`, `kalkan-setup`, bootstrap) | `--no-cache-dir` |

The work folder of a tool run goes after a successful run; after a failed run it stays in the run (with the opengrep log) until `kalkan run clean`. After the change the same measurement showed no file of a kalkan tool outside the kalkan folders; the remaining changes came from other programs. `tests/unit/test_tool_footprint.py` asserts the environment of each tool. With `@pytest.mark.tools`, `tests/integration/test_tool_footprint.py` runs the opengrep probe and scan, gosec and govulncheck with a profile of their own and checks that the profile stays as it was; against the code before the change it fails with the paths above.

Not measured: Linux and macOS (the same variables are set; macOS takes the Go configuration folder from `HOME`, which kalkan leaves alone, so Go telemetry follows your own setting there), `kalkan sca update-db`, and a `kalkan tools install` that downloads.

**Files of older versions.** kalkan 1.6.1 and earlier wrote the folders above: `~/.opengrep` (the log holds paths and code of audited targets), `%LOCALAPPDATA%\opengrep`, `%LOCALAPPDATA%\go-build`, `%APPDATA%\go\telemetry` and the pip cache. kalkan does not delete them, because other programs can use them. Delete them by hand when nothing else uses them.

## Residual risks

- **The main session follows your permission mode.** In plugin mode the orchestrating session uses your own permission settings. The hook denies its network tools only while an audit runs in it, and only for the calls that reach the hook. `bypassPermissions` removes every prompt for the other calls. A hook `deny` still applies in that mode: measured on 2026-10-16 with Claude Code 2.1.301 (`claude -p --permission-mode bypassPermissions` with a test plugin whose hook denied Bash and WebFetch; both calls were blocked).
- **Other subagents in an orchestrating session.** Whether Claude Code gives a subagent call the `session_id` of its parent session is not documented and not measured. If it does not, the network tools of a non-kalkan subagent in that session follow the normal flow. The kalkan subagents are always confined by `agent_type`.
- **The network word list is a heuristic.** A Bash command can reach the network through an interpreter without a URL or one of the words. The hook does not see it.
- **Not every subagent call reaches the hook.** Edit, MultiEdit and Bash commands without `kalkan` or a network word do not start the launcher (speed for other sessions). The tool list of the kalkan agents keeps these tools away from them: Claude Code offers an agent only the tools of its list.
- **A session mark can outlive a stopped run.** When a session stops in the middle of an audit, its network tools stay off for up to 6 hours. While any mark exists, Read, Grep, Glob and Write calls of every session start Python in the hook (about 0.4 s each, measured).
- **The proxy trap sees proxy-aware clients only.** All Go tools, Python and git honor the proxy variables, and so does Kingfisher (Rust; the control steps saw its update check and its validation). A tool that opens a direct connection would not be seen by the test. A DNS lookup is not seen either; ShellCheck and flawfinder have no network code.
- **Inline vacuum ignores stay effective.** vacuum 0.33.0 has no option to turn off the `x-lint-ignore` keys of an OpenAPI document, so a target can hide a vacuum result with one (the status file counts them, `inline_ignores`).
- **Helm charts are scanned with their default values.** helm-checkov renders each chart with its own `values.yaml` only; other values files of the target are not rendered. A chart whose dependencies are missing from `charts/`, or that does not render with its defaults, is a scan gap. The template lines of the results are a best-effort mapping from the rendered manifests.
- **Inline ShellCheck directives stay effective.** ShellCheck 0.11.0 has no option to turn off `# shellcheck disable=` comments, so a target can hide a ShellCheck result with one (the status file records the source as honored, ADR-0003). Trivy's `trivy:ignore` comments are the same case.
- **The history copy starts git in the original repository.** `git clone --no-local` runs `git upload-pack` in the original repository to read the objects. upload-pack writes nothing; the test checks every file, folder and modification time. A repository that another user owns gets no history copy (git refuses it: `safe.directory`).
- **Go in local mode** cannot download modules. Packages whose modules are neither in the local module cache nor in a `vendor` folder load with errors: the type-based checks of gosec are partial for them, and govulncheck stops for that module. Both cases are listed (`partial_packages`) and shown as a scan gap; `kalkan scan gosec --online`, `kalkan sca reach --online` or a `vendor/` folder in the target closes the gap. The Go database is as old as the last `update-db`. kalkan turns Go telemetry off for its own Go processes on Windows and Linux; on macOS it follows your own `go telemetry` setting (the default `local` uploads nothing).
- **Old databases.** Local matching knows only the vulnerabilities of the last `update-db`. `kalkan doctor` warns after 7 days.
- **CI/CD checks in local mode.** zizmor runs no online audit (impostor commits, known vulnerable actions and stale action refs need the GitHub API), and Scorecard runs no check that needs the network (`Pinned-Dependencies`, `Vulnerabilities`, `Fuzzing`). On Windows, poutine 1.1.6 and Scorecard 5.5.0 see no GitHub workflow; their status files list the missed files (`platform_gap`).
- **Codex mode** has no tool list per agent. A Codex subagent has a shell; the network is off in the sandbox, but read-only access and the single result file depend on the instructions.
- **Checkout mode** has no deny rule for edits outside `runs/` (see promise 2). The project settings apply only in a trusted folder (docs/ENGINE-SPEC.md section 21).
