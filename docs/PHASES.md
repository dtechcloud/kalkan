# Phase engine

This document is the contract for `kalkan.run.phases`, `kalkan.run.steps`, `kalkan.run.plan`, `kalkan.run.handlers.*`, `kalkan.run.prompts` and the commands `run next`, `run step`, `run answer`, `run reopen` and `task prompt`. It extends docs/ENGINE-SPEC.md sections 11 and 18–20. Phase order: `prep`, `deterministic`, `sca`, `recon`, `plan`, `hunt`, `validate`, `poc`, `merge`, `report`, `done`.

Modules: `phases` (decision loop, phase entry, `run answer`), `steps` (engine steps, `run step`), `plan` (ledger units, hunt waves, critic), `validation` (verify tasks for hunter candidates and deterministic tool results), `review` (final review tasks, step `review:tasks`), `consolidate` (consolidation tasks, step `consolidate`; the engine rules live in `kalkan.findings.consolidate`), `polish` (Turkish letter tasks, step `polish`; the engine rules live in `kalkan.findings.polish`), `inputs` (task inputs), `prompts` (rendering), `recon_merge` (step `recon:merge`), `ledger_store` (ledger reads and validated writes), `tasks` (task creation with prompt), `runfiles` (derived run files), `cleaning` (text, paths, fingerprints).

## 1. The decision loop (`run next`)

`run next --owner <name> [--limit N] [--run] --json` releases expired leases (under the run lock) and returns exactly one action:

1. In phase `done` with `incomplete_reason` set: `{"kind": "incomplete", "reason": ..., "report": "<run dir>/report/REPORT.md"}`. An incomplete reason never stops the loop before `done` (section 7).
2. In phase `done` otherwise: `{"kind": "done", "report": "<run dir>/report/REPORT.md"}` (relative to the working folder when possible, else absolute).
3. For the current phase P (entered first, see below), in this order:
   1. The first open step of P (status `pending`, or `running` with a dead process). It runs only when P has no `pending` or `leased` task (every step waits for the tasks of its phase) → `{"kind": "engine_step", "phase": P, "step": <name>}`. When a live process runs the open step → `{"kind": "wait", "retry_after_seconds": 60, "reason": ...}`.
   2. Claimable tasks of P (status `pending`, dependencies settled) → claim up to `limit` (default `options.max_parallel`) for the owner, render any missing prompt → `{"kind": "agent_tasks", "phase": P, "tasks": [{"id", "type", "agent", "prompt_file", "result_file"}]}`. With `--limit 0` no task is claimed (the action is `wait`).
   3. Tasks of P that are leased (or pending but not claimable) → `{"kind": "wait", "retry_after_seconds": 60, "reason": ...}`.
   4. A pending question → `{"kind": "ask_user", "question": "english_report"}`.
   5. A phase hook may add work (hunt: the critic; report: the translation tasks); then the loop repeats.
   6. Otherwise P is complete: P becomes `done`, the next phase becomes current and the loop repeats.

Entering a phase (`ensure_entered`): when the current phase has status `pending`, its entry hook creates its tasks (with dedupe keys) and returns its steps; one transaction then adds the steps and sets the phase to `running`. A crash during the entry repeats it without duplicates. `run next` never runs a long step; `run step` also enters the phase first. A tools-only run skips its agent phases here (section 3, tools-only runs).

Examples:

```json
{"kind": "engine_step", "phase": "deterministic", "step": "scan:trivy"}
{"kind": "agent_tasks", "phase": "recon", "tasks": [{"id": "T0002-recon", "type": "recon", "agent": "kalkan-recon", "prompt_file": "C:/.../runs/<id>/tasks/T0002-recon/prompt.md", "result_file": "C:/.../runs/<id>/tasks/T0002-recon/result.json"}]}
{"kind": "wait", "retry_after_seconds": 60, "reason": "agent tasks of this phase are leased"}
{"kind": "ask_user", "question": "english_report"}
{"kind": "done", "report": "runs/<id>/report/REPORT.md"}
{"kind": "incomplete", "reason": "validation_budget_exhausted", "report": "runs/<id>/report/REPORT.md"}
```

## 2. Engine steps (`run step`)

`run step [--max-seconds 480] [--run] --json` runs the first open step of the current phase:

1. Under the lock it picks the step and records `running` with `pid`, `host`, `started_at`, `timeout_seconds` (= `--max-seconds`) and `attempts` (the start count). A `running` step whose PID is dead on this host, or that is older than `timeout_seconds + 120`, counts as open again. A step that started 3 times without finishing becomes `failed` ("started 3 times without finishing"), so a step that kills its process never loops.
2. Without the lock it runs the step function. A missing optional module or function gives `skipped` with `module_unavailable: <module>`. A `KalkanError` or any other exception gives `failed` with the message. A failed step never stops the run; the report shows it.
3. Under the lock it records the outcome (`status`, `detail` (at most 2,000 characters), `finished_at`, `duration_seconds`; `pid` and `host` are removed), when the step still carries this process's PID.

Output: `{"phase", "step", "status", "detail", "duration_seconds"}`. `status` is `done`, `failed` or `skipped`; `idle` when no step can run now (no open step, or the phase still has open tasks; `step` names the waiting step or is null) and `busy` when a live process runs the step. Example:

```json
{"phase": "deterministic", "step": "scan:matcher", "status": "done", "detail": "ok: 3 candidates; 79 of 204 matchers applied, 3 files scanned (3 candidates)", "duration_seconds": 0.412}
```

Time limits: scanner steps pass `timeout_seconds = max(5, min(adapter.timeout_seconds, max_seconds - 20))` to `run_adapter`. `sca:sbom` and `sca:match` run two tools each, so each tool gets half of `max_seconds - 20`; `sca:govulncheck` gets `max_seconds - 20`. Steps are idempotent: a repeated run produces the same files.

## 3. Phases

**deterministic.** Entry: one step `scan:<engine>` per adapter of `kalkan.scanners.registry.SCANNERS`; an adapter whose `applies(ctx)` is false is recorded as a `skipped` step with its reason. Without `kalkan.scanners` one step `scan` is `skipped` (`module_unavailable: kalkan.scanners.registry`). Each step calls `kalkan.scanners.base.run_adapter` (which ingests SARIF into `candidates.json`). Status: `ok` → `done`, `skipped` → `skipped`, `failed` and `timeout` → `failed`.

**sca.** Steps `sca:sbom` (`kalkan.sca.commands.run_sbom`), `sca:match` (`run_match`), `sca:govulncheck` (`run_reach(max_tasks=0)`; `skipped` without `sca/vulns.json`, without Go records, or when the adapter does not apply) and `sca:reach_tasks`. The last step selects records with `kalkan.sca.reach.select_for_agents` (remaining budget = `budget.available(state, "sca_reach")`, at most `budget.sca_reach_cap(state)` = one quarter of the validation reserve; critical and high records only; the most severe record of each package first, then the second of each package, and so on), creates one `sca_reach` task per record (phase `validate`, input from `build_reach_input`, dedupe key `sca_reach:<ref>`, priority 80 for critical, else 70) and records the task IDs with `mark_reach_tasks`. The steps never hold the run lock while they call `kalkan.sca` (it takes the lock itself).

**recon.** Entry: four `recon` tasks (`kind` = product, principals, surfaces, execution; priority 90; dedupe key `recon:<kind>`) when the budget can fund all four (`budget.available(state, "recon") >= 4`); otherwise no task and the pending incomplete reason `budget_cannot_fund_reconnaissance_and_reserves` (section 7). Input: `kind`, `tech`, a file inventory (`total_files`, top-level entries with file counts, file counts by extension, manifest paths; capped near 400 JSON lines), the deterministic summary (candidate counts by engine, class and severity; the 20 files with most candidates) and the SCA summary (records by severity, the ten most severe). Step `recon:merge` (runs after the recon tasks settle) writes:
- `recon/architecture.md`: the four summaries under headings (each cut to 275 words; a missing result says so), then a surface table (at most 60 rows); about 1,500 words at most;
- `recon/surfaces.json`: `{schema_version, surfaces, id_map}`; surfaces without duplicates by (kind, file, line, name), renumbered `S001`, `S002`, …; each surface keeps its `sources` (`<task-id>:<original id>`); `id_map` maps every original ID to the new one; a surface with an unsafe file path or without a name is dropped;
- `recon/classes.json`: `{schema_version, classes, from_recon, from_candidates}`: the union of `classes_of_interest` and the classes of deterministic candidates with severity medium or higher (without `vulnerable-dependency` and `code-quality`).

**plan.** Step `plan:ledger` builds `coverage-ledger.json` (Cloudflare format, validated with `kalkan.findings.ledger.validate_ledger` before every write; always written, also when empty):
- Groups (`plan.subsystem_groups`): recon agents name one subsystem in different ways (the first live run had `shop/accounts` and `accounts`, `config` and `configuration`). Surfaces that share a file or a subsystem label form one group; its name is the most frequent label (ties: UTF-16 order), or the folder of its first file (`plan.folder_of`: the first two folders, `(root)` for a top-level file) when no surface has a label. `unknown subsystem` counts as no label.
- Unit levels, fine to coarse (`plan.LEVELS`): `surface` = (surface, class); `file` = (file, class), the surfaces of one file merge; `subsystem` = (group, class); `folder` = (folder of the file, class); `all` = (`all-in-scope-code`, class). `standard` and `deep` start at `surface`, `fast` at `subsystem`. The planner (`plan.choose_units`) takes the first level from the start whose hunt batches fit `budget.hunt_wave_cap(state)`; at `all` the units that do not fit become `deferred`. Every unit records its level in the bookkeeping field (`kalkan.level`), and gap units (hunt `uncovered`, critic `missing_units`) use the level of the wave-1 plan, so a gap inside a coarse unit maps to the same `coverage_id` (the critic then reassigns that unit).
- Classes of a unit: the run classes that fit the kinds of its surfaces (section 5), plus the classes of deterministic candidates (severity low or higher) in their files. `vulnerable-dependency` and `code-quality` never become units.
- `canonical_refs` (attack_class always `knowledge/classes/<slug>.md#Summary`; `coverage_id` = `kalkan.findings.ledger.canonical_coverage_id`): `surface` level: surface `<file>#<surface name>`, boundary = the surface trust boundary text, subsystem = the group. `file` level: surface `<file>#all-entry-surfaces`, boundary `<file>#all-trust-boundaries`, subsystem = the group. `subsystem`, `folder` and `all` levels: surface `<group>#all-entry-surfaces`; `fast` uses the fixed subsystem identity `profile/quick/all-in-scope-subsystems` (Cloudflare rule) and the boundary `profile/quick/all-trust-boundaries`; `standard` and `deep` use the boundary `<group>#all-trust-boundaries` and the group as subsystem. The human fields equal the references (the attack class uses the slug), so one semantic tuple always maps to one ID. Units with the same `coverage_id` merge (starting paths, surface IDs, weakest auth). `ordinary_attack_class_block` = the attack-class reference; `selected_companion_blocks` = `knowledge/domains/<pack>.md#Core discipline` and `#Validation rules` of every domain pack that lists the class; `prior_status: "none"`.
- Bookkeeping field `kalkan` on every unit (allowed by the Cloudflare format): `surface_ids`, `kind` (the surface kind, or `mixed`), `auth` (the weakest: `none`, `unknown`, `user`, `privileged`), `hints`, `group` (the batching group), `level` and `origin` (`plan`, `hunt:<task>` or `critic:<task>`). A unit that the critic closed from sibling coverage also has `closure` (section 3, hunt).
- Priority: `auth: none` first, then units with deterministic hints, then the class weight (3 for injection, access control, SSRF and similar classes; 1 for CORS, open redirect, misconfiguration, DoS, rate limits, IPC, code quality; 2 otherwise), then `coverage_id`.
- Budget (`kalkan.run.budget`): the validation reserve is `ceil(max_agent_tasks × 0.45)`. A hunt batch holds at most `budget.batch_size(state)` units of one group (fast 6, standard 4, deep 3). One hunt task expects two verify tasks (`VERIFY_PER_HUNT`), so a wave plans at most `budget.hunt_wave_cap(state)` = `min(available(hunt), (remaining − critic reserve left − review reserve left) // 3)` new hunt tasks (computed once per wave); the critic reserve and the validation reserve stay free. Units that would need a further batch become `deferred` with reason `budget_cannot_reserve_critics_and_validation`. The step detail names the level, for example `31 units (folder level): 31 planned, 0 deferred (hunt budget 10)`.

Step `plan:tasks` creates the wave-1 `hunt` tasks (phase hunt, `meta.wave = 1`, priority 70 when a unit has `auth: none`, else 60, dedupe key `hunt:w1:<sorted coverage IDs>`) and sets their units `in_progress` with the owner = lower-case task ID. It creates no verify task: hunter verify tasks come after each hunt wave and deterministic verify tasks at the end of the hunt phase (section 3, hunt).

**hunt.** Hunt handler (section 4). Hunt waves: the profile's critic wave count (fast 1, standard 2, deep 3) is also its hunt wave count. When every task of the hunt phase is settled, the hook `hunt_idle` runs:
1. Units of settled hunt tasks that are still `in_progress` (a dead hunt) go back to `planned` (Cloudflare: a failed conclusion leaves the unit planned).
2. `validation.allocate_hunter_verifies` creates the verify tasks of all hunter candidates so far (section 4.2). A candidate without budget sets the pending incomplete reason `validation_budget_exhausted`.
3. Without hunt tasks the phase ends; planned units become `deferred` (`hunt_not_started`).
4. When the critic of the current wave n exists, it already scheduled wave n+1 or deferred the work: the phase ends; remaining planned units become `deferred` (`critic_failed` for a dead critic, else `hunt_waves_exhausted`).
5. With a pending incomplete reason, hunting stops; planned units become `deferred` (`validation_budget_exhausted`).
6. Otherwise one `critic` task of wave n (phase hunt, priority 85, dedupe key `critic:w<n>`) is created when `budget.available(state, "critic") >= 1`. Without budget, the run gets the pending incomplete reason `critic_budget_exhausted` and planned units become `deferred` with that reason.

When the phase ends (steps 3, 4 and 5, and a critic that cannot be funded), `validation.create_deterministic_verifies` creates `verify` tasks (phase validate, `subject.kind = deterministic`, dedupe key `verify:deterministic:<candidate id>`) for deterministic candidates with severity critical or high, a safe file and a start line, in code classes (not `vulnerable-dependency`, not `iac-cloud-container`), one per (class, file, start line), only when no hunter candidate cites the same class and file (sink file or an evidence file; the hunters saw the tool results as hints), ordered by severity, engine, file, line and ID, capped at `budget.deterministic_verify_cap(state)` (one quarter of the validation reserve) and at `budget.available(state, "verify")`. A tool result without a verify task stays in the report as an unverified tool result.

The critic handler (section 4) adds the accepted `missing_units` as planned units of wave n+1 (deduplicated by `coverage_id`), archives reassigned units into `attempts` (Cloudflare rules), closes the accepted `covered_ids` entries (below) and creates hunt wave n+1 for every planned unit when n+1 is within the wave count and no incomplete reason is pending. Otherwise the planned units become `deferred`: `fast_profile_final_critic` (fast: exactly one hunt wave and one final critic, as in the Cloudflare quick profile), `hunt_waves_exhausted`, or `validation_budget_exhausted`. The decision depends on the accepted work, not on `stop` alone (Cloudflare: "the parent's loop condition, not stop alone, decides").

Closures from sibling coverage (`critic.close_units`, after the reassignments, in every profile and wave): a `covered_ids` entry closes a `blocked` unit whose unresolved facts other units already settled. The engine accepts an entry only when the unit exists, is not in `reassign_ids` and is live `blocked`; every `covered_by` unit exists, is not the unit itself and is `covered` or `candidate` from its own hunt (a unit with a live closure of any critic never settles another unit, so closures never chain); and every `evidence` quote names a file in the `reviewed_paths` of the `covered_by` units and matches the source (`quote_verify.verify_evidence`). Otherwise the entry is dropped with `duplicate_entry`, `unknown_unit`, `reassigned`, `not_blocked`, `sibling_not_covered`, `quote_outside_sibling_paths` or `unverified_quote`; the first entry of a `coverage_id` decides. The engine checks that the quotes exist in code that the siblings read. Whether that code answers the unresolved facts is the critic's judgment, as in consolidate. An accepted unit keeps its owner and the hunter's checks and gets one more `source` check (`agent_id` = lower-case critic task ID, the quoted files, the invariant names the `covered_by` units and the unresolved facts, the result is the critic's reason); then `status: covered`, empty `unresolved` and `kalkan.closure` = `{task, covered_by, unresolved, reason, evidence}`. A later reassignment archives the closure check with the attempt and removes `kalkan.closure`; a re-applied result of the unit's hunter replaces the closed state and removes it too. The critic input marks these units `closed_from_siblings`. The upstream `resolved_prior_leads` field marks prior leads resolved; kalkan closes ledger units instead, with quotes. In the .NET deep audit of 2026-10-16, sibling units covered 3 of the 4 open units, and the report still showed a partial pass.

**validate.** `verify` and `sca_reach` tasks, then the final review (Cloudflare Phase 5, "verify the final records with fresh eyes"), then the root-cause consolidation, then the Turkish letters of a Turkish run. Handlers in section 4. Entry: three steps in this order, `review:tasks` (`budget.REVIEW_STEP`), `consolidate` (`budget.CONSOLIDATE_STEP`) and `polish` (`budget.POLISH_STEP`); in the profile `fast` the review step is recorded as `skipped` ("fast profile: no separate final review ..."), because the Cloudflare quick profile merges the record checks into the validation pass. The review step runs when every verify and sca_reach task is settled (`kalkan.run.review.create_review_tasks`):

1. It merges the findings of the done verify tasks exactly as `kalkan.findings.merge` does (same `id` or `fingerprint`, `merge_with_sources`), so one task reviews one final record.
2. Every final `confirmed` and `needs_validation` record (rejected records get no review) gets one `review` task (phase validate, dedupe key `review:<fingerprint>`, priority 70 for confirmed and 50 for needs_validation, `meta = {finding, fingerprint, verdict, verify_tasks}`) while `budget.available(state, "review") >= 1`. Order: every confirmed record first, then the needs_validation records; inside each group the higher severity score first (confirmed: likelihood + impact of the record; needs_validation: the suggested severity of the claim, or the tool severity), then the fingerprint.
3. A confirmed record without budget sets the pending incomplete reason `review_budget_exhausted` (Cloudflare: never skip the review of a confirmed record). A needs_validation record without budget stays unreviewed; the report counts it.
4. Input (`inputs.review_input`): `subject {finding_id, fingerprint, verdict}`, `checklist` (the Cloudflare Phase 5 items of the verdict, `kalkan.findings.review.CHECKLISTS`) and `finding` = the canonical record without `audit_answers`, `engines`, `candidates`, `owasp`, `poc`, `i18n` (`review_record`). The reviewer never sees the verifier's answers or the hunter text.

The step detail names the counts, for example `3 review tasks for 3 records` (plus `; 1 without budget (0 confirmed, 1 needs_validation)`). The review tasks then run in the same phase.

The step `consolidate` runs when every task of the phase is settled: after the review tasks in `standard` and `deep`, after the verify and sca_reach tasks in `fast` (`kalkan.run.consolidate.create_consolidate_tasks`). Verifiers run in parallel and see only the claims near their own code, so one root cause can survive as several final records filed under different classes or anchored in different files. Evidence overlap alone is not enough (a backup job that fills a shared disk and the same job that follows symbolic links share the code path, not the flaw), so an agent judges and the engine decides:

1. Records: the final records exactly as merge would write them now (`kalkan.findings.merge.merged_records` without folding, so the review outcomes apply); only `confirmed` and `needs_validation` records with an id take part (no rejected record, no record that a review rejected).
2. Links (`kalkan.findings.consolidate.link_reasons`), any of: (a) `shared_location`: a common cited location, the same file and lines at most 3 apart, across `evidence[]` and every `audit_answers.*.evidence[]`; (b) `nearby_anchor`: the first `evidence` items in the same file at most 15 lines apart; (c) `same_class_file`: the same `class` and a common cited file (the files of rule a).
3. Candidate groups: the connected components (union–find) with at least two records. A component of more than 12 records is split into `ceil(n / 12)` chunks of nearly equal size in breadth-first order over the links (records in order of first evidence file and line, then fingerprint), so a chunk keeps linked records together and never holds a single record; the task input says so (`component.note`).
4. One `consolidate` task per group (phase validate, priority 60, dedupe key `consolidate:<fingerprints in UTF-16 order, space separated>`, a SHA-256 for a long key; `meta = {findings, chunk, chunks}`) while `budget.available(state, "consolidate") >= 1`, the group whose best record ranks highest under the primary rule first. Input (`inputs.consolidate_input`): `records` (per record the id, fingerprint, verdict, class, CWE, title, description and root cause (each cut at 1,200 characters), the remediation strategy (400 characters), the overall severity, the evidence locations, the verified audit-answer quotes, a trace summary `<kind> <file>:<line>` and the review decision), `links` (`{ids, reasons}` per linked pair) and `component` (`{size, chunk, chunks, note}`).
5. A group without budget stays unchecked: its records stay separate findings. It never blocks the report and sets no incomplete reason; the step detail, the event `consolidate_unfunded` and `consolidate/groups.json` record it, and the report lists a warning.
6. `consolidate/groups.json` = `{schema_version, records, groups: [{ids, fingerprints, component_size, chunk, chunks, task}], unfunded}` (`task` null without budget).

The step detail names the counts, for example `1 consolidate tasks for 1 candidate groups (3 records)` (plus `; 1 groups without budget (their records stay separate)`), or `no candidate group (2 records)` (no task). The consolidate tasks run in the same phase. Merge folds the accepted groups (ENGINE-SPEC section 15).

The step `polish` is the last step of the phase: it runs when every task of the phase is settled, so after the consolidate tasks, in every profile (`kalkan.run.polish.create_polish_tasks`). In a Turkish report, agents sometimes write Turkish prose without the Turkish letters, also in the top rows of the executive page. The agent prompts require the Turkish alphabet (rule 8 of `_common.md`), but a model can still slip. A program cannot restore the letters ("sinir" is "sinir" (nerve) or "sınır" (limit)), so an agent restores them and the engine accepts only a change of those letters:

1. Language: a run whose language is not `tr` gets the step `done` with the detail `not a Turkish run` and no task.
2. Records: the final records exactly as merge would write them now (`kalkan.findings.merge.merged_records` with folding: the review outcomes, the consolidation and the corrections of earlier polish tasks apply); `confirmed` and `needs_validation` records with an id take part, folded duplicates included; rejected records never.
3. Prose fields (`kalkan.findings.polish.prose_fields`), each addressed by a path in JSON-pointer form: `/title`, `/description`, `/root_cause`, `/claimed_root_cause`, `/intended_behavior`, `/trace/<n>/description`, `/evidence/<n>/description`, `/conditions/<n>/description`, `/execution/attacker_perspective`, `/execution/instructions/<n>`, `/execution/observed_result`, `/remediation/strategy`, `/severity/likelihood/reason`, `/severity/impact/reason`, `/confidence/reason`, `/blockers/<n>`, `/validation_plan/local`, `/validation_plan/deployment`, `/audit_answers/<attacker_control|privilege_boundary|unmitigated>/reason`, `/review/reason`, `/duplicate_reason` and `/related/<n>/reason`. Payloads, code changes, file names, scopes, quotes, ids, fingerprints and the English `i18n` texts are no prose fields.
4. Selection (`needs_polish`): a field needs the letters when it has at least 20 letters, none of `çğıöşüÇĞİÖŞÜ`, and at least one letter outside the code tokens (rule 5 of section 4, polish; a field that is only code, such as the engine blocker `confirmed_fields_missing`, has nothing to restore). A field that the input of a done polish task already held with the same text is not selected again, so a second run of the step never asks twice about a field that the agent left as it was.
5. Batches: the records with at least one such field, confirmed first, then by overall severity (highest first), then by id, at most 8 per task. One `polish` task per batch (phase validate, priority 40, dedupe key `polish:<record ids> <SHA-256 of the selected (id, path, text) triples>`, a SHA-256 for a long key; `meta = {findings, fields}`) while `budget.available(state, "polish") >= 1`. Input (`inputs.polish_input`): `{records: [{id, title, fields: [{path, text}]}]}` with only the fields that need the letters; the title comes for context also when it needs none. `KNOWLEDGE` is the glossary.
6. A batch without budget keeps its text. It never blocks the report and sets no incomplete reason; the step detail, the event `polish_unfunded` and `polish/batches.json` record it. When no batch can be funded, the step is `skipped` (`no budget: 2 polish batches (12 records) keep their text`).
7. `polish/batches.json` = `{schema_version, records, selected, fields, batches: [{ids, fields, task}], unfunded}` (`task` null without budget).

The step detail names the counts, for example `2 polish tasks for 9 of 47 records (31 fields)` (plus `; 1 batches without budget (their records keep their text)`), or `no record needs the Turkish letters (47 records)` (no task). The polish tasks run in the same phase; the phase ends when they are settled. Merge applies the accepted corrections after the folding (ENGINE-SPEC section 15).

**Older run states.** A run that entered `validate` before these steps existed has no `consolidate` or no `polish` step. When such a run resumes in a running `validate` phase, `ensure_entered` adds the missing steps as `pending` in their place of the order `review:tasks`, `consolidate`, `polish` (event `step_added`, `reason: "older run state"`), so they run after the open tasks of the phase. A run already past `validate` continues unchanged; `run reopen` brings it back.

`run reopen --step consolidate|polish [--run] --json` (`phases.reopen`): under the run lock it refuses (`StateError`, exit code 1) while a task is leased or a live process runs a step. A run in the phase `poc`, `merge`, `report` or `done` goes back to `validate`: the phase is `running` again with the named step and every step after it `pending` (`consolidate` also puts back `polish`, because polish selects from the folded records; `polish` leaves `consolidate` as it is; a missing step is added in its place of the order), and the later phases are `pending` without steps, so their entry hooks add the steps again. Tasks, answers (an `english_report yes` gives the translation and `report:en` again, the done translation tasks are reused through their dedupe keys) and the incomplete reason stay; the event `run_reopened` records `step` and `previous_phase`. A run in any other phase is not changed, so a second call is a no-op. Output: `{run_id, step, previous_phase, phase, reopened}`. `run next` then runs the step and hands out its tasks (existing ones are reused through their dedupe keys), and the run flows through merge, report and done again. A run from before both steps that gets `run reopen --step polish` also gets `consolidate` back when `validate` resumes (older run states, above), and it runs first.

**poc.** `sandbox_status(ctx)` is true only when `options.docker` is not `off`, `kalkan.sandbox` provides callable `run_poc` and `docker_available`, and `docker_available()` is true. Then the entry creates one `poc_build` task per confirmed or needs_validation code finding (budget permitting; dedupe key `poc:<finding id>`) and the step `poc:run` (after the tasks) calls `run_poc(ctx, task_id, harness)` for every harness and writes its `poc.json`. Otherwise (Docker is off or absent, ADR-0006) one step `poc:skip` writes, for every confirmed and needs_validation code finding (class not `vulnerable-dependency` or `iac-cloud-container`; a finding whose final record a review rejected is left out, `review.rejected_verify_tasks`), `tasks/<verify-task>/poc.json` = `{finding_id, level: "unit", status: "blocked", observed_result: "sandbox_unavailable", artifacts: [], blocker: "sandbox_unavailable"}` next to the finding's `finding.json`, plus a summary `poc/skip.json` (`{reason, blocker, findings: [{finding_id, task}]}`). The report localizes the `observed_result` key `sandbox_unavailable`; the English reason stays in the step detail and in `poc/skip.json`. `kalkan.findings.merge` reads `poc.json` from every done task, so the verify task directory carries it; no synthetic task is needed.

**merge.** Step `merge` runs `kalkan.findings.merge.merge_run(run_dir)` while it holds the run lock.

**report.** Step `report:<lang>` (the run language): when an incomplete reason is pending, it first sets `incomplete_reason` (section 7); then `kalkan.report.commands.write_report(run_dir, kalkan.report.model.build_model(run_dir), lang, formats=("md", "html", "exec", "sarif", "json", "sbom"))`. When the run language is `tr` and the step is done, the question `english_report` is pending until it is answered (`run answer`). An English run asks nothing. After `yes` the report hook creates `translate` tasks (batches of at most 20 findings of `findings.json`, phase report, dedupe key `translate:<n>:<first id>`, not counted against the budget) and the step `report:en`, which runs merge again (to apply the translations as `i18n.en`), writes `REPORT.en.md`, `REPORT.en.html` and `EXECUTIVE.en.html`, and refreshes `findings.sarif`, `findings.json` and `summary.json` in the run language. `no` finishes the phase. Headless runs answer `no`.

`run answer <question> <value> [--run] --json`: `question` is `english_report`; `value` is `yes`/`no`, also `evet`/`hayır` (`y`, `e`, `n`, `h`). Output `{"question", "value", "previous", "reopened"}`. `yes` after the run reached `done` (and is not incomplete, and has no `report:en` step yet) puts the run back into the report phase (`reopened: true`), so `run next` drives translate → `report:en` → `done` again. An unknown question or value gives exit code 4.

**Tools-only runs** (`options.mode` = `tools-only`: `run init --tools-only`, `kalkan audit --tools-only`; ENGINE-SPEC sections 11 and 25). The engine never creates an agent task, and the budget is 0:

1. `ensure_entered` skips every pending agent phase in a row (`phases.AGENT_PHASES`: `recon`, `plan`, `hunt`, `validate`, `poc`) before it enters the next phase: in one transaction the phase becomes `skipped` with `started_at` and `finished_at`, its steps are exactly `{"tools-only": {"status": "skipped", "detail": "tools-only mode: no agent validation; all results are unverified tool results"}}` (`phases.TOOLS_ONLY_STEP`, `phases.TOOLS_ONLY_REASON`), the next phase becomes current, and the event `phase_skipped` records `phase`, `next` and `reason`. `run next` and `run step` both enter through it, so the run goes from `sca` straight to `merge`. No hook of a skipped phase runs (no `hunt_idle`, no deterministic verify tasks).
2. The entry of `sca` records `sca:reach_tasks` as `skipped` (`phases.TOOLS_ONLY_REACH`); `sca:sbom`, `sca:match` and `sca:govulncheck` run as usual.
3. `pending_question` returns None: the run asks nothing and reaches `done` after the report step. `run answer english_report yes` still reopens the report phase; the report hook then adds `report:en` without translation tasks.
4. The report shows the reason as the first partial pass reason (ENGINE-SPEC section 16).

An agents run (no `mode` field) never takes these paths.

## 4. Task handlers (`kalkan.run.handlers.<type>.handle(ctx, task, result)`)

Every handler is idempotent (derived files are written atomically and keyed by task ID; follow-up tasks use dedupe keys) and raises `ValidationError` for a result that is valid JSON Schema but semantically wrong (the attempt then counts as failed).

- **recon:** the result's `kind` must equal the input `kind`. The result stays in `result.json`; `recon:merge` reads all done results.
- **hunt:** semantic checks: `units` names every assigned coverage ID exactly once (assigned = the input units); every candidate belongs to an assigned unit; a `candidate` unit has at least one candidate; `covered` and `blocked` units have none; `covered` has no unresolved fact and `blocked` has one; every check keeps at least one safe path and visible text. For each candidate: the trace is normalized first (`cleaning.normalize_trace`, section 4.3), then the Cloudflare fingerprint (section 4.1) and the status of every evidence quote (`quote_verify.verify_evidence`, stored as `quote_status`) are computed. The handler creates no verify task; every candidate starts as `pending` and the allocation after the wave decides (section 4.2). The ledger update is checked on a copy, then written under the lock: every unit owned by this task (or still `planned`) gets the status, `local_checks` (`agent_id` = lower-case task ID, `method: "source"`, `artifact: null`), `reviewed_paths` (the union of the check paths), `result_fingerprints` (candidate units, including duplicates) and `unresolved`. A unit owned by another agent is left alone. `uncovered` entries become `planned` units of the next wave. `tasks/<id>/candidates.json` = `{task_id, wave, candidates: [{index, ref, coverage_id, fingerprint, title, class, cwe, file, line, quotes, verified_quotes, suggested_severity, normalized, status (pending, queued, duplicate, unvalidated), verify_task, duplicate_of}]}`; `normalized` lists the trace repairs. A repeated handler run keeps the allocation of a candidate whose fingerprint did not change. `hardening` stays in `result.json` (the report reads it).
- **critic:** as in section 3 (hunt). `tasks/<id>/critic.json` = `{task_id, wave, stop, added_units, reassigned_units, closed_units, closures: [{coverage_id, covered_by, reason, evidence (with quote_status and in_sibling_paths), accepted, dropped}], outcome, hunt_tasks, deferred_units}`.
- **verify:** the result's `subject` must equal the input subject. Cosmetic slips of an honest result are repaired first and listed in `verdict.json` `normalized` (section 4.3). `quote_verify.evaluate(result["audit_answers"], get_lines)` gives the verdict. When the verdict is `confirmed`, the result must hold every confirmed-branch field (`intended_behavior`, `conditions`, `execution`, `remediation`, `severity`, `confidence`); a claim that the quote check downgrades needs no confirmed-branch field. The finding keeps only the fields of its branch: `confirmed` gets `root_cause`, `intended_behavior`, `conditions`, `execution` (`observed_result` gets the prefix "Yalnızca statik analiz (PoC çalışmadı):" or "Static analysis only (no PoC ran):" unless it already says so), `remediation`, `severity` (`overall_severity` capped at the impact) and `confidence` (`high` lowered to `medium`); `needs_validation` gets `claimed_root_cause`, `blockers` (the agent's blockers, then the engine reason codes `unverified_evidence` and `ungrounded_refutation`; `unknown:<question>` when nothing else names a blocker) and `validation_plan`; `rejected` gets `claimed_root_cause` and `reason`. Extensions: `class`, `cwe` (the result's, normalized, else the class default), `owasp` (taxonomy, for example `A03:2021`), `engines` (`hunter` or the deterministic engine, plus `verifier`), `candidates` (deterministic subjects), `audit_answers` (verified), `id` (`assign_finding_ids` with `make_get_lines(target)`). A `duplicate_of` that names a known claim (not for `rejected`) gives the finding the primary claim's fingerprint, so merge keeps one record with the strongest verdict. `validate_findings([finding])` must pass; then `tasks/<id>/finding.json` and `tasks/<id>/verdict.json` (`{task_id, verdict, reasons, fingerprint, computed_fingerprint, duplicate_of, duplicate_honored, finding_id, normalized}`) are written.
- **review:** the result's `finding_id` must equal the input subject. `checks` holds every item of the record's checklist exactly once and nothing else. `verified` must not fail a check; only `severity` and `remediation` may fail when the result gives the corrected field (a contradictory result counts a failed attempt). Every `evidence` quote is checked with `quote_verify.verify_evidence`. The applied decision (`kalkan.findings.review.apply_review`, a reviewer never promotes a record):
  - `reject` needs at least one verified quote: the record becomes `rejected` with the reason as `reason` (`claimed_root_cause` = the old root cause) and stays in `findings.json`. A `reject` without a verified quote is applied as a `downgrade` with the extra blocker `ungrounded_rejection`.
  - `downgrade` of a confirmed record with a `severity` that lowers it (`lower_severity`: each of likelihood and impact takes the proposed score only when it is lower, the overall severity is the lower overall value and never exceeds the new impact) keeps the record confirmed with that severity. Without a lower severity the record becomes `needs_validation`: the reason is its blocker and the validation plan is the verifier's plan of a verify task of the record (else an engine plan in the run language).
  - `downgrade` of a needs_validation record adds the reason to its blockers.
  - `verified` adds `reviewer` to `engines`. A confirmed record that stays confirmed takes a lower severity and a corrected remediation (code changes with an unsafe file name are dropped); its confidence stays at most `medium`. A needs_validation record takes no severity and no remediation.
  - Every reviewed record gets `review = {decision, reason}`. The handler applies the decision to the input record and validates the result (`validate_findings`); then `tasks/<id>/review.json` = `{task_id, finding_id, fingerprint, verify_tasks, verdict_before, requested, decision, reason, severity, remediation, blockers, validation_plan, verdict_after, checks, evidence (with quote_status), verified_quotes, normalized}`. Merge applies it to the merged record (ENGINE-SPEC section 15).
- **consolidate:** every input id appears exactly once across `groups[].ids` and `distinct[].id`; an unknown id, an id named twice and a missing id each fail the attempt. Every `evidence` quote of a group is checked with `quote_verify.verify_evidence` (the cited line plus and minus 2 lines); a group with a quote that does not match is dropped (`accepted: false`, `dropped: unverified_quote`), and its records stay separate. For each accepted group the engine picks the primary (`kalkan.findings.consolidate.pick_primary`): the highest verdict rank (confirmed > needs_validation), then the highest overall severity, then the most `evidence` items, then the smallest id; the other members become its duplicates. `tasks/<id>/consolidate.json` = `{task_id, records, groups: [{ids, reason, evidence (with quote_status), verified_quotes, accepted, dropped, primary, duplicates}], distinct, accepted, dropped, normalized}`. Merge folds the accepted groups.
- **polish:** the agent proposes, the engine decides field by field (`kalkan.findings.polish.check_correction`). The input must hold at least one field. Every returned field is judged in result order on the NFC form of its text (a letter written with a combining mark counts as the letter) and rejected, with a reason, when:
  1. `(id, path)` is not a field of the input: `unknown_field`;
  2. the result named the field before: `duplicate_field` (only the first one counts);
  3. the new text equals the old one: `unchanged`;
  4. `fold(new) != fold(old)`, where `fold` maps ç→c, ğ→g, ı→i, ö→o, ş→s, ü→u, Ç→C, Ğ→G, İ→I, Ö→O, Ş→S, Ü→U and changes nothing else (so only those letters can differ; the length and every other character stay): `fold_mismatch`;
  5. a code token is not byte-identical: `code_token_changed`. Code tokens, in the old and in the new text: everything between a backtick run and the next run of the same length (an unmatched run makes the rest of the text code), and every whitespace-separated token whose core (the token without leading `"'“‘«(` and trailing `.,;:!?…"'”’»)`, so that the full stop of a sentence is no code) contains one of `_ . / \ ( ) [ ] { } < > = : # $ @ % & | * + ~ ^ ;`, a digit next to a letter, or an uppercase letter after its first character (`IsEmailVerified`, `X-Forwarded-For`, `SQL'i`).

  A rejected field never fails the task; the old text stays. `tasks/<id>/polish.json` = `{task_id, applied: [{id, path, old, new}], rejected: [{id, path, reason}]}`. Merge applies the accepted corrections.
- **sca_reach:** `vuln_ref` must equal the input; every evidence quote is verified with `quote_verify.verify_evidence`; then `kalkan.sca.reach.apply_reach_result(run_dir, result, verified)` (without holding the lock). `tasks/<id>/reach.json` records the quote statuses (`applied: false` without `kalkan.sca`).
- **poc_build:** `finding_id` must equal the input; harness paths must be unique and safe; the compose file a safe target path. `feasible: false` → `tasks/<id>/poc.json` with `status: blocked`, the reason as `observed_result` and `blocker: sandbox_infeasible`. `feasible: true` → `tasks/<id>/harness.json` for `poc:run`; without a sandbox `poc.json` records `not_run` with `blocker: sandbox_unavailable`.
- **translate:** the result must translate exactly the findings of the input; then `tasks/<id>/translations.json` = `{translations: [...]}`.

`get_lines(path)`: `kalkan.run.source.make_get_lines(target_dir)`: accept only safe relative paths, resolve inside `target/`, refuse symlinks, bounded reads, cache per path, return `text.split("\n")` or None.

### 4.1 Fingerprints

`<class>:<sink file>:<sink scope>`; the sink is the first `sink` trace element, else the last element (after the trace normalization of section 4.3 the sink is always the last element); without a scope `line-<n>` stands in. Every run of characters outside `[A-Za-z0-9._:/@+-]` becomes `-` (underscores and spaces too), repeated dashes collapse, leading characters that are not ASCII letters or digits are removed, the result is cut to 400 characters; an empty result is `unknown`.

### 4.2 Verify tasks for hunter candidates (`validation.allocate_hunter_verifies`)

The hook `hunt_idle` runs the allocation when every task of a hunt wave is settled, before the critic of the wave. It reads the candidates of all done hunt tasks, so a later wave sees the decisions of the earlier ones:

1. Claims with the same fingerprint are one claim; its primary is the first by task sequence and index. Claims with the same class, sink file and sink line (another scope label for the same root cause) join one root-cause group.
2. Groups are ranked by their best member: suggested severity (impact + likelihood, informational 0 … critical 4; a missing value counts as medium) first, then the presence of a verified quote, then the fingerprint (Cloudflare fingerprint order).
3. In that order each group gets one `verify` task while `budget.available(state, "verify") >= 1` (phase validate, `subject = {kind: hunter, ref: "<task-id>#<index>"}` of the representative, input from `inputs.verify_input_hunter` with the normalized trace, priority `30 + 6 × (impact + likelihood)`, priority 10 without a verified quote, dedupe key `verify:fp:<fingerprint>`, `meta = {subject, fingerprint, file, title}`). A group whose fingerprint already has a task keeps it.
4. A group without budget stays unvalidated: its items get status `unvalidated`; every `candidate` unit of an item gets `validation_budget_exhausted: <fingerprint>` in `unresolved`; the run gets the pending incomplete reason `validation_budget_exhausted`.

Item statuses afterwards: `queued` (the primary of a group with a task), `duplicate` (another claim of the group; `duplicate_of` names the primary, `verify_task` its task) and `unvalidated`. The function is idempotent and returns `{fingerprints, groups, created, reused, unvalidated}`.

### 4.3 Normalizing honest results (`cleaning.normalize_trace`, `cleaning.normalize_path`)

The finding validator is strict about form. An honest agent result can fail it for cosmetic reasons (the first live run lost two verify tasks to `trace[2].kind: must be "propagation", got "sink"`). Before the checks the engine repairs these slips and records each repair:

- Trace kinds: a multi-step trace gets `entrypoint` first, `sink` last and `propagation` between; the agent's order of steps stays. A one-step trace keeps `entrypoint` or `sink` (any other kind becomes `sink`). Exact duplicate steps are removed, also when the new kinds make two steps equal. Hunt candidates and verify results both use it, so the fingerprint is computed from the normalized trace.
- Cited paths in the trace, the evidence and the audit-answer evidence lose `./` prefixes and use `/` (only when the result is a safe relative path; an unsafe path stays and the validator rejects it). The quotes and lines never change, so quote verification is as strict as before.
- Exact duplicate evidence, conditions and payloads are removed. A remediation code change whose file name is not a safe relative path is dropped.
- A `needs_validation` finding without a visible validation plan (typically a claim that the quote check downgraded) gets an engine plan in the run language that names its blockers.

The verdict rules, the quote check, the confirmed-branch fields and unsafe trace or evidence paths are never relaxed.

## 6. Prompt rendering (`kalkan.run.prompts`)

`render(ctx, task_type, task_id, input) -> str` builds `_common.md` + `<type>.md` + `_footer.md` with the placeholders of ENGINE-SPEC section 19, in one pass (a placeholder inside inserted text is never expanded; unknown placeholders stay). `TARGET_DIR` and `RESULT_FILE` are absolute POSIX paths; `SCHEMA` is the compact JSON of the result schema; `EXAMPLE` is `kalkan/prompts/examples/<type>.json`.

`KNOWLEDGE` (`kalkan.run.knowledge`): `recon` and `critic` get the methodology; `hunt` the methodology, the hunter extract of every unit class (each class gets an equal share of the space, at least 1,500 and at most 12,000 characters), the language packs of the detected tech, and the `Core discipline` and `Validation rules` sections of the domain packs of the unit classes; `verify` and `review` the methodology and the verifier extract of the class (nothing for a null class); `sca_reach` the `vulnerable-dependency` verifier extract; `poc_build` the poc-builder extract of the class; `translate` and `polish` the glossary. Every block starts with a `#### <title>` line. The whole block is capped at 24,000 characters and cut at a heading or paragraph boundary.

`SOURCE_EXCERPTS` uses `quote_verify.numbered_source` around the cited locations (trace and evidence for `verify` (`input.claim`), `review` and `poc_build` (`input.finding`), `locations` for `sca_reach`): a window of 40 lines per location (19 lines before, 20 after; lines 1–40 for a location without a line), overlapping windows of one file merged, 400 lines in total, each line cut at 500 characters, in a fence longer than any backtick run of the excerpt. A file that `get_lines` cannot supply says so.

The prompt is written to `tasks/<id>/prompt.md` right after the task is created (`kalkan.run.tasks.new_task`). `ensure_prompt` renders a missing prompt again; `run next` calls it for every task it hands out and `task prompt <id> [--run] [--json]` calls it before printing (`--json`: `{id, prompt_file, prompt}`).

## 7. Incomplete runs (Cloudflare incomplete-run rule)

A run ends in one of two states: `done`, or `incomplete_reason` set with its exact reason and the gap disclosed in the report. A reason found during the run goes to the state field `incomplete_pending` (the first reason wins); the run continues, so validation, merge and the report still run. The step `report:<run language>` copies `incomplete_pending` into `incomplete_reason` before it renders (the report shows it as a partial-run reason); entering `done` does the same when the report step was skipped. An incomplete run still reaches phase `done`: the report phase finishes normally (the `english_report` question too), and only in phase `done` does `run next` return `{"kind": "incomplete", "reason", "report"}` instead of `done`. The skill then summarizes the partial report like a done run and names the reason; `kalkan unattended` stops with exit code 1. `english_report yes` after an incomplete run also reopens the report phase. Reasons:

- `budget_cannot_fund_reconnaissance_and_reserves`: the recon entry cannot fund the four recon tasks after the reserves; no recon task runs.
- `validation_budget_exhausted`: the verify allocation after a hunt wave (section 4.2) cannot fund a verify task for a root-cause group. Its candidates stay unvalidated (`candidates.json` status `unvalidated`), their units get the unresolved fact `validation_budget_exhausted: <fingerprint>`, they never become findings, and hunting stops (no further critic or wave). The report lists every unvalidated fingerprint with its title, class, suggested impact and likelihood, location and ledger units in section 1 (Cloudflare: the first section of a partial report lists them), and `summary.json` carries them under `unvalidated_candidates`.
- `critic_budget_exhausted`: the critic of a wave cannot be funded.
- `review_budget_exhausted`: the step `review:tasks` cannot fund the review of a confirmed record. The record stays as the verifier built it; the report counts it as not reviewed.

## 8. State fields added by the phase engine

- Step records: status `running`; optional `pid`, `host`, `timeout_seconds`, `attempts`, `duration_seconds` (`check_state`: a `running` step needs a `pid`).
- Top level: optional `incomplete_pending` (string or null), and `answers` (`{"english_report": "yes" | "no"}`).
- Options: optional `mode` (`agents` or `tools-only`; see section 3, tools-only runs). A phase of a tools-only run can be `skipped` with the one step `tools-only`.
- Task `meta`: `{kind}` (recon), `{wave}` (hunt, critic), `{subject, fingerprint, file, title}` (verify), `{finding, fingerprint, verdict, verify_tasks}` (review), `{findings, chunk, chunks}` (consolidate), `{findings, fields}` (polish), `{vuln_ref}` (sca_reach), `{finding}` (poc_build).

## 9. Choices where the original contract was silent, and deviations

- Every step waits until its phase has no open task (section 1). This orders `recon:merge` after the recon tasks and `report:en` after the translations without per-step rules.
- Verify tasks for hunter candidates are created after each hunt wave for all candidates at once, ranked by suggested severity and then by fingerprint (Cloudflare validates "in fingerprint order"). When the validation budget runs out, the least severe groups stay unvalidated. Candidates with the same class, sink file and sink line merge into one root-cause group (one verify task) even when their scope labels differ.
- Unit granularity adapts to the budget (section 3, plan): `standard` and `deep` start at (surface, class) like Cloudflare, but coarsen to (file, class) and further when the hunt batches do not fit; `fast` starts at (subsystem, class). The first live quick run on a 403-line app made 210 units (141 deferred) and 23 hunt tasks, and only 4 of 22 hunter fingerprints got a verify task; the same situation now gives 31 units, 6 hunt tasks and a verify task for all 22 (`tests/integration/test_budget_simulation.py`).
- The `poc:skip` output goes into `tasks/<verify-task>/poc.json` (the option "files of a synthetic engine task", without a synthetic task); `poc/skip.json` is only a summary. ENGINE-SPEC section 15 names this location.
- Translation tasks do not count against the agent budget: the user asks for them after the audit.
- The validation reserve is 45 % of the budget (Cloudflare suggests 30 % "when in doubt"). The SCA reachability and the deterministic verify tasks each use at most one quarter of it, so hunter candidates keep at least half. Deterministic verify tasks run only for tool results that no hunter candidate cites.
- A dead critic ends the hunt phase (its planned units become `deferred` with `critic_failed`).
- The PoC sandbox path (`poc_build` tasks and `poc:run`) is active since ADR-0006: `kalkan.sandbox` provides `run_poc` and `docker_available`. With Docker the run creates the `poc_build` tasks and takes `poc:run`; without it (or `--docker off`), `poc:skip`. App-level harnesses start the target's compose stack on an internal network (ADR-0008). Pulling or building its images needs the opt-in `--allow-build-network`.
- The final review is a step inside `validate`, not a new phase: a new phase would change `PHASES` and the state schema and break the resume of a run that started before the change; a step reuses the rule "a step waits for the tasks of its phase" (as `sca:reach_tasks` and `plan:tasks` create tasks). A run that entered `validate` before the review step existed has no step and no review.
- Cloudflare Phase 5 returns `verified` or a complete replacement record and sends a material replacement to another fresh verifier. kalkan had no PoC run when the review was added, and it keeps the engine as the only author of records: the reviewer returns a decision, the checklist and quotes, plus an optional lower severity and a corrected remediation. The engine never promotes a record and never raises a severity, so no second reviewer is needed. A separate root cause that a reviewer notices goes into its reason only.
- The review reserve is one quarter of the validation reserve (`budget.review_reserve`, 0 in `fast`); verify, sca_reach and poc_build tasks cannot use it, and `hunt_wave_cap` keeps it free. When the step `review:tasks` or the `validate` phase has finished, the unused part is free again.
- Reviews apply in merge before the PoC results. The PoC phase skips a record that a review rejected.
- Consolidation is a step inside `validate` for the same reason as the review (no new phase, no state schema change). It has no reserve of its own: `consolidate` is a validation task type, so it can use the free pool and what is left of the validation reserve; a group without budget stays unchecked and never makes the run incomplete. The groups are funded in order of their best record, so the most severe duplicates fold first.
- The handler picks the primary from the records that the agent saw; merge picks it again with the same rule on the final records (a PoC result between validate and merge could change a verdict). A group that overlaps a group of an earlier consolidate task, or that names fewer than two eligible records at merge time, is skipped with a warning (conservative: the records stay separate).
- Chunks of a split component have nearly equal sizes (`ceil(n / 12)` chunks), so no chunk holds a single record that could not be grouped.
- The Turkish letter restoration is a step inside `validate` for the same reason as the review and the consolidation. Like `consolidate`, `polish` is a validation task type without a reserve of its own: it uses the free pool and what is left of the validation reserve, and a batch without budget keeps its text and never makes the run incomplete.
- Polish selects from the folded records, so `duplicate_reason` and `related[].reason` are prose fields, and merge applies the corrections after the folding. A `/title` correction also updates the `related[].title` copies of that title on the primary record. `merged_records(fold=False)` (the input of the consolidate step) stays without the corrections.
- A field needs at least one letter outside the code tokens: a field that is only code can never pass the code-token check, so selecting it would only cost agent work.
- Execution payloads and remediation code changes are not prose: a payload or a code line must stay byte-exact, and the code-token check cannot see a string literal as code.
- A field that a done polish task already showed to an agent is not selected again (also after `run reopen`), so a field that the agent left as it was, or whose correction the engine rejected, keeps its text instead of costing a new task on every reopen.
- A field named twice in one result is rejected as `duplicate_field` (only the first one counts) instead of failing the attempt: the task contract says that rejected fields never fail the task.
- Merge checks every correction again (the field still holds the old text, the letter check passes) and validates the corrected record; an invalid record gets its old fields back with a warning. So `findings.json` never takes a text that the handler would refuse, and the merge step never fails because of a correction.
- Limits: a field with fewer than 20 letters (a short title) or with one Turkish letter already (a partial slip) is not selected; the code-token rule cannot tell an English prose word from a Turkish one, so the agent prompt carries the rule that English words stay.
